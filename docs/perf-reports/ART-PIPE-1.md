# ART-PIPE-1 性能レポート（雷神剣の雷 B「ひかりの たま」）

- 判定: **合格**（重大 0 件・軽微 4 件）。比べた元は main（fd7e4dc）の今の雷。実装はコミット 2d39663 まで。
- 測り方: `e2e-perf/thunder.perf.ts`（`PERF_LABEL=main|branch`、`PERF_SCENE=flat|roof|sky`、`PERF_DSF=1|2`）。`npm run perf` の設定（`playwright.perf.config.ts`、小ブロックありの本番どおり）で動く。
  1 コマ = `step(1)` ＋ 描画 ＋ 1 点の readPixels（SwiftShader の描画をその場で終わらせる）。
  シェーダー（WebGL プログラム）の数と中身・GPU メモリは、WebGL の呼び出し（linkProgram・texStorage2D など）を init script で数えた（src は触っていない。main にも同じ物差し）。
  雷神剣を 60 ステップ ため → 放す → F1〜F88 → そのあと 60 コマ、を 3 回くり返す（1 回目・2 回目・3 回目）。窓 1280×800、クラウドはソフトウェア描画なので時間は絶対値でなく **main との差と比** で読む（1 コマが約 250〜290 ms）。計測のゆれは ±10% 前後。
- 注意: 計測の初期に、放した 1 コマ目（F1）が main でも 1 秒前後になる外れ値が出た（描画のたまりを流していなかった）。そこで放す前に 3 コマ流してから測る形に直した。下の数はその後。

## シェーダー（プログラム）の数（落雷なし → 最初の落雷）

増えた 22 個（1 回目の落雷の F1〜、材質ごと）:
- 雷 B 自分の 4 つ: 雷の 3 板（`uDepth`・`uSheet`）・輪（`uRect`）・つぶ（`aCell`、インスタンス）・うつす板 blit（`tDepth`・`uAmount`）。※輪は main にもあったが材質が別なので 1 つ増える。
- **世界の材質が「RT に描く版」として作りなおされる 18 個**（ブロック・妖怪・柱などの `map` 付き材質。色空間・トーンマップが画面と違うので、three が別プログラムにする）。これが F1 の +500 ms の大半。
- 空を向けた場面でも同じ（+18、材質が少ないぶん 20 → 38）。

## GPU メモリの見つもり（Retina pixelRatio 2 = 2560×1600 の実測）

| 項目 | main | 雷 B | 増え |
|---|---|---|---|
| 雷の絵 | 地面の絵 256×1024（1.0 MB） | 3 まい: 雷 1024×1024（4.2 MB）＋輪 256×128 ＋つぶ（0.1 MB 未満） | +約 3.3 MB（見こみ 4 MB 内） |
| 落雷中の RT 色（sRGB8） | なし | 16.4 MB | +16.4 MB |
| 同 深さ（24 bit） | なし | 16.4 MB | +16.4 MB |
| 合計 | 約 1 MB | **約 37 MB**（Retina）。1280×800 では約 12.5 MB | 見こみの約 50 MB より小さい（色が 8 bit のため） |

- **RT は落雷のあとも残る**: 最初の落雷で作ってから、ページを閉じるまで delete は 1 回も呼ばれない（`deleteTexture/Framebuffer/Renderbuffer` の数が落雷の前後で同じ）。うごかない 37 MB。M4（共有メモリ）では 37 MB は問題にならない大きさ。

## 原因の分析

1. **最初の落雷の 1 コマ（F1）だけ重い**: 世界を RT に描く道を初めて通るため、世界の材質 18 個＋雷 B の 4 個＝22 プログラムをそのコマでコンパイルする。2 回目からは再利用（F1 は main と同じ）。M4 の実機ではソフト描画より短い見こみだが、コンパイルは GPU でなく CPU・ドライバの仕事なのでクラウドの値（+約 500 ms）と同じ向きの「ひっかかり」が出うる。**放した瞬間は画面が見せ場で、止まると目立つ**。
2. 落雷中の +5〜10%: 世界の絵を RT に描いたあと、画面ぜんたいに 1 枚 blit（深さを書きもどす）する分。クラウド（ソフト描画で画素数が時間に効く）の値で、本物の GPU では 1 画面ぶんの blit は小さい。描画回数は main より少ない。
3. 落雷のあとは RT が残るだけで、毎コマの仕事は main と同じにもどる（落雷後 250 ms 台）。
4. S=null（空が見えない・はずれ）: `ThunderFx.onEvent` は `e.S` が null のとき `timeline.start` を呼ばないので `active()` は false → **RT の道を通らない**（コードで確認）。台帳の「S=null でも RT を通る」は現在のコードでは当たらない。実測の「sky」場面（カメラを空へ向けた）は S が取れて通常の落雷になってしまい、S=null の再現はできなかった。**本当に無駄なのは「屋根の下」（S あり・skyVisible=false → 量 0）**。光が出ないのに 88 ステップ RT 経由になり、落雷なしより +0〜20 ms（ゆれの範囲）で、描画回数 +4。

## 改善案（効き目の見こみと見た目への影響。直すなら perf-engineer へ）

| 優先 | 案 | 効き目の見こみ | 見た目への影響 |
|---|---|---|---|
| 1 | **ウォームアップ**: 起動後の空き時間（またはため始めの 1 回）に、小さい RT（例 64×64）へ世界と雷 B の材質を 1 回描く（`renderer.compile(scene, camera)` を RT 指定で）。あるいは 雷神剣を持った瞬間に 1 回 | 最初の落雷の F1 の +約 500 ms を、見えない時間に動かす（22 プログラムをふだんの 1 コマに分散するか、起動の 5 秒以内に入れる）。起動時間は +0.2〜0.5 s の見こみ（要測定） | なし |
| 2 | **S あり・skyVisible=false（屋根の下）では RT の道を通らない**（量 0 のとき `active()` で RT を使わず、深さを読む雷の板だけ通常描画で描く、または板の「深さでうすく」を省いて通常の道へ） | 屋根の下の落雷で RT・blit・コンパイルをなくす（描画 +4・ソフト描画で +0〜20 ms）。屋根の下では最初の F1 のコンパイルも出ない | 屋根の下でブロックにささる所の「4 段のうすれ」が変わる（板が手前の壁から出るのでほぼ同じ）。要スクショ確認 |
| 3 | **RT を落雷のあと捨てる**（F89 から 2〜3 秒後に `dispose()` して null）。または解像度を画面の 0.5〜0.75 倍に | Retina で約 33 MB 解放（常駐 37 → 4 MB）。ただし次の落雷で作りなおし（1 コマ +数 ms）。M4 では 37 MB は小さいので優先は低い | 解像度を下げると明るさ・うすれの縁がぼやける。捨てるだけなら変化なし |
| 4 | 世界の材質のコンパイルを減らす: RT の出力設定（色空間・トーンマップ）を画面と同じにして、three が同じプログラムを使い回せるか確かめる（18 個が 0 になれば案 1 も不要） | F1 の +500 ms と 起動への加算を ほぼ 0 に | なし（色が変わらないことを確認） |

## 指摘（重大度つき。台帳 `docs/loop-ledger/ART-PIPE-1.md` へ perf として追記する分）

- 【軽微】最初の落雷の F1 で材質 22 個（雷 B 4 ＋ 世界 18）をコンパイルして +約 500 ms（ソフト描画）。2 回目から差なし。上の案 1 か 4。M4 実機で F3 を見て 100 ms を超えるなら重大に引き上げ。
- 【軽微】RT（色＋深さ、Retina 約 33 MB）が落雷のあとも残る。M4 では問題にならない大きさ。案 3。
- 【軽微】屋根の下（S あり・量 0）の落雷でも 88 ステップ RT の道を通る。案 2。S=null は現在のコードでは通らない（台帳の記述を直す）。
- 【軽微】落雷中は main より +5〜10%（blit 1 回ぶん、ソフト描画の値）。描画回数は main より少ない（112 対 117）。

重大 0 件 → 合格。

## オーナーに Mac で確認してほしい場面（F3 で fps と 1 コマの時間を見る）

1. **最初の落雷**: アプリを開いた直後（落雷を 1 回も打っていない状態）で、雷神剣を 60 ステップ以上ためて放す。放した瞬間にひっかかるか（F3 の最悪値が 100 ms を超えないか）。2 回目からは同じ場所で滑らかか。
2. 広い所（妖怪が 10 体以上・遠くまで見える）で落雷中（約 1.5 秒）の fps が 60 のままか。放したあとに 60 へもどるか。
3. 屋根の下（洞くつ・家の中）でも落雷を放ち、光が出ない代わりに重くならないか。
4. 画面を大きくしたり Retina のままで数回打って、メモリ（アクティビティモニタ）が増え続けないか（RT は 1 回作ったら使い回し）。
