## 測りの書き足し（`e2e-perf/budget.perf.ts`）
- `SectionMesher.prototype.start` / `resume` の包み: 分けて作った 1 セクションぶん（start から結果が返るまで）の resume の合計 ms と回数を `P.mesh`（`sliced` に回数）に入れた。`build` の中の start/resume は二重に数えない（`P.inBuild`）。`step`（段）の包みで 段ごとの 1 単位の時間（n・合計・最大）も取る。

## 分析: どこが重いか（基準 2 の不合格の原因）

1. **一番の原因は予算の使い方。** `ChunkStream.step` の予算 `BUDGET_TOTAL_MS = 8` を 小ブロックの続き（resume）が 毎コマ ほぼ丸ごと使う。resume の p95 は 8.2〜8.3 ms で、締め切りを 1 単位ぶん（0.1〜0.5 ms）こえて止まる。これに 1 コマの そのほかの仕事（物理・描画準備・箱・光の列など 0.5〜1 ms）が足されるので、仕事が残っている間は p50 が 8.5〜8.9 ms になり、約 7 割のコマが 8 ms を超える。「1 コマの最大は 予算 ＋ 1 単位」という票の見積もりは当たり（最大は 19〜38 ms から 飛びを除く）が、**予算が 8 ms ちょうどだと p95 ≤ 8 ms には原理的にならない**。
2. 時々の大きな超え（16 ms 超え 1〜6 コマ、最大 19〜38 ms）は、1 単位が 8〜19 ms かかった回（planes 19.3・occupancy 8.6・sample 8.3 など。ほとんど 1 回きりの飛び）と、箱・`lightColumn`（BASE と同じく 8 ms 超えが 0〜3 回で 最大 7〜12 ms）が 続きの 8 ms に足された回。`finish` 段は最大 1.9 ms で、extras は重くない。
3. メッシュ以外の原因: box 18〜32 コマ、lightColumn 7〜22 コマ、generate 1〜2 コマ、取りつけ 0〜1 コマ（8 ms 超えのコマの中で いちばん大きい部品としての数）。続きの時間を除いても over8 ≤ 30 は ぎりぎり（box + lightColumn だけで 25〜48 コマ）。

## 改善案（優先度順。src は直していない）

1. **【重大】小ブロックの続きの締め切りを 8 ms でなく、残り予算に合わせて 5〜6 ms にする。** 例: `deadline = t0 + totalMs - (そのコマで すでに使った箱・光・列の ms) - 1.5`。または 小ブロックの続きだけ `BUDGET_TOTAL_MS - 2.5`。効く見こみ: 続きが毎コマ 8 ms 使うのをやめれば、p50 は 6.5 前後・p95 は 7〜8 ms に収まる見こみ（未検証。要・再測定）。代わりに 差しかえの速さは 6/8 に落ちる（今の 差しかえ待ちが増える方向）ので、基準 5 を 再測定で見る。
2. **【軽微】飛びをおさえる:** occupancy（`OCC_ROWS`）・sample・planes の 1 単位が 8〜19 ms になる回がある。`OCC_ROWS` を半分に、`PLANES_PER_STEP` を 1 に（または 単位の時間を `now()` で見て 打ち切る）。
3. **【軽微】`lightColumn`・箱（8 ms 超えの原因 合わせて 25〜48 コマ）:** この票では分けない決め。続きの予算を減らす（案 1）と、同じコマに重なる回が減る。それでも over8 が 30 を超えるなら 次の票で `lightColumn` を分ける。
4. **【軽微】歩く間の 差しかえの遅れ:** 待ち行列が 66〜250 まで残る（前 0〜18）。案 1 で続きの予算を減らすと さらに増えるので、遠い所を後回しにする順序（プレイヤーに近い順）は 保ったまま、立ち止まったら 予算を増やす（立っているコマは 0.5〜1 ms しか使っていない）手がある。

## オーナーに Mac で確認してほしい場面（F3 で fps を見る）

1. 起動してすぐ（`?nosave=1` なしでも可）、はらっぱをまっすぐ走る（Shift ＋ W、ジャンプを混ぜる）。F3 の fps とカクつきを見る。前は 一定の間隔でコマが止まった（1 回 30〜115 ms）。あとは 止まりが小さくなっているはず。120 fps 近く出ている Mac では、毎コマが 8〜9 ms（約 110〜120 fps）まで使われるので、F3 の fps が 60 を大きく割っていないかを見る。
2. もり（木が多い所）を走って、地面や木が 箱 → 小ブロックに替わる様子が 遅すぎないか（足もと 16 ブロックは 全部すぐ小ブロックのはず）。遠くの木の替わりは 前より遅れるので、遅れが気になるか。
3. よる（`時間 = よる`、たいまつを置く）を走って、同じカクつきがないか。
4. 着いた直後（ワープ直後）の 数秒のカクつきが 前と変わらないか。

## 測りのゆれ・取れなかった点
- 時間の時計（`clock=time`）なので、同じ手順でも 1 回ごとに ±10〜30% ゆれる（arrive.ms、立つ p95 の yoru など）。p95・over8 は 6 場面で ほぼ同じ値（10.1〜11.1 / 395〜507）に集まり、3 回の測りでも順位は変わらなかったので、基準 2 の不合格の判定は ゆれの影響を受けない。
- 原因別の数は 1 コマの中の部品の時間（計測の包みの時間）から 判定した推定。コマの GC 停止やブラウザの描画待ちは 部品に入らず `other` に入る。
- 指摘台帳 `docs/loop-ledger/PERF-2.md` への追記は、この依頼のコミット対象外のため まだ書いていない（上の 改善案 1 が 重大な指摘）。

- p95 は「予算 ＋ 約 1.5 ms」で、p50 が 6.0 を こえると p95 が 8 に届く。立っている間の p50 が高い よる（立つ p95 6.5〜9.6 ms）は その分 悪く、よる かげ オンが 最後まで 8.3〜8.6 / over8 40〜50 で残った（3 / 2.5 の 2 回めで 8.4 / 41）。
- 2 回測った同じ設定でも ±0.5 ms・over8 ±10 ゆれる（このマシンで 小ブロックの数も 38〜84 とゆれる）。

### 両方を満たす点が見つからなかった理由
- 小ブロックの差しかえは 全部で 合計 約 3 s の CPU（歩く 600 コマ）。予算が 5〜5.5 ms（引く量 2.5〜3）だと 600 コマ ぶんで 3.0〜3.3 s で、ちょうど足りなくなる。p95 ≤ 8 に必要な p50 ≤ 6（予算 ≲ 5.5）と、足もとが遅れない予算（≳ 6.5。前回 8 ms では 0 / 12 件）が 重ならない。
- 引く量 2〜2.5 では 基準 5 が 1〜2 場面、3 では 3〜4 場面で 1〜3 セクション落ちる。足もとの仕事に 引く量を 減らす手（上の 2.5 / 1.5 など）は よる の p95 を 8 超えに戻す。
- 残る差は「歩き終わりの瞬間に 足もとの 1〜3 セクションが まだ箱」。遊びの上では 立ち止まれば すぐ 小ブロックになる（待ちが短い）ので、オーナーの Mac の F3 で見て 気になるかを決めてほしい。直すなら 次のどちらか（PO に相談）: (1) 仕事の順を「列の輪」でなく 実際の距離（プレイヤーから 16 ブロック以内を先）にする（count の時計の順も変わるのでテストに影響）。(2) 初めて作る箱・LOD（優先 1）が 差しかえ（優先 2）より先に並ぶ決まりを 時間の時計だけ 変える。
- よる かげ オンの p95 は 立つ間の p95（6〜9 ms）が高いことの つづき。メッシュの予算では 下がらない（別の票: よるの描画・光）。
