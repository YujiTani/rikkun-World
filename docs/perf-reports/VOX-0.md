# VOX-0 性能レポート（9×9×9 の試しの場面）

- 判定: **合格**（重大な指摘 0 件。ただし「本物の fps」はオーナーの Mac 確認待ち）
- 計測シナリオ: `e2e-perf/voxelProto.perf.ts`（`npm run perf -- e2e-perf/voxelProto.perf.ts` → `perf-results/voxel-proto.json`）。全 7 方式を、島 `generateIsland` の本物の世界で、固定の 2 か所（スタート地点・島の上空）から測る。
- 計測日: 2026-10-16 / クラウド（GPU なし・SwiftShader、1280×720）。**fps は目安にならない**ので、三角形・描画回数・メモリ・作る時間で比べる。
- 比べる前の注意: ここは「論理ブロックは今のまま、見た目だけ 9×9×9」「光なし」の試作。ゲーム本体は光の計算なども入るので、本番は同じ数でもやや重くなる。

## 計測の確かめ（数が正しいか）

| 確かめた点 | 結果 |
|---|---|
| 三角形・描画回数 | `renderer.info.render` を、慣らし 2 回のあと 1 回描いた直後に読む（毎回リセットされる設定）。**合っている**。視錐台の外のチャンクは数えられない（スタートは島の中心を向くので約半分が外）。 |
| `geometryBytes` | index＋全 attribute の `byteLength` の合計。上空（全部が見える）では 1 四角 = 52 バイト（頂点 4×(位置 6＋aData 4)＋index 12）で、14.35M 三角形 → 7.18M 四角 × 52 = 373MB と**ぴったり合う**。**合っている**。ただし「見えているメッシュ（visible）のぜんぶ」で、視錐台の外も入る。だからスタートでは、三角形に対してバイトが多めに見える（三角形は視野の中だけ）。 |
| メモリの数え方の限界 | 数えているのは JS 側の配列の大きさ。three は GPU に上げたあとも CPU 側の配列を持ち続けるので、実際の使用量は**ほぼ 2 倍**（CPU＋GPU）。また `hybrid` は近さが変わって見えなくなったメッシュを捨てずに隠すだけ（`ProtoScene.update`）なので、歩きまわると数えていない分が増える（計測は毎回 `clearAll` してから測るので影響なし）。 |
| `buildAllMs` | `clearAll` のあと `applyCamera`（= 見える全チャンクの micro/box/lod を作る。遠くの LOD も含む）の時間。合っている。ただし 1 回だけの測定で、先に走った方式が JIT の暖まり代を払う（hybrid の「上空で足した分」が r=16 で 331ms、r=24 で 57ms とぶれるのはこのため）。**±30% くらいの誤差**として読む。 |
| `rebuildChunkMs` | スタート地点のチャンクの `buildMicro`（メッシュ作り＋BufferGeometry 作り＋`computeBoundingSphere`）を 20 回の中央値・最大。GPU への転送は含まない（描いたときに行われる）。`current` の 0.8ms は「光なし・メッシュだけ」の値で、ゲーム本体の 135.8ms（光の更新など込み、#28）とは別物なので、**方式どうしの比べにだけ使う**。 |
| `renderCpuMs` | **使えない**。`gl.finish()` を入れても 1ms 前後（SwiftShader は別プロセスで描くので、JS は待たない）。1400 万三角形でも 2ms。→ 代わりに `syncRenderMs`（描いたあと `readPixels` で待つ。描き終わるまでの時間）を足した。これは CPU で絵を描く時間なので絶対値は Mac と無関係だが、**方式の比べには使える**。 |
| 計測シナリオの不具合 | スクショを `docs/` に書くたびに vite が画面を作り直し、`window.__voxelProto` が消えて途中で落ちることがあった（1 回目の実行で再現）。→ スクショは最後にまとめて書くように直した（`e2e-perf/` の中だけの変更）。 |

小ブロックの形で描くチャンクの数（スタート）: 全方式 40（48 ブロック以内）、hybrid は r=16 で 8、r=24 で 15、r=32 で 20（あとは箱＋模様）。遠く（48〜88）の LOD は 24 チャンクで全方式同じ。

今の描き方との比（スタート）: naive 194 倍、greedyShape 138 倍、hybrid r=16 29 倍、r=24 57 倍、r=32 66 倍（三角形）。

## 原因の分析

1. **主因は「でこぼこの形そのものが作る面の数」**。色の持ち方ではない。
   - 近い 1 チャンクが約 8.4 万三角形（greedyShape）。今の 1 チャンクは約 600。草の上 1〜2 段のふさ・表面 1 段のへこみで、1 ブロックの上面が「平らな 1 枚」から「小さな段差だらけ」になり、横の面（段差の壁）が大量にできる。
   - greedy は高さがそろった所しかまとめられない。段差が細かいので、naive → greedyColor で 1%、→ greedyShape（色を見ずに形だけまとめる）で 29% しか減らない。**まとめ方の工夫（greedy・3D テクスチャ）では桁が変わらない**。
2. **距離ごとに描き分ける（hybrid）が一番効く**。近くだけ小ブロックの形にすると、三角形は greedyShape の 1/5（r=16）〜1/2（r=24〜32）、頂点データは 1/7〜1/2、全体を作る時間は 1/6〜1/2。
3. 描画回数は、どの方式も 190〜550 以下で問題になる水準ではない（チャンク数に比例。チャンクは 16×16 で 2〜3 メッシュ）。hybrid r=16 は 73 回で今の 56 回とほぼ同じ。
4. **1 チャンクの作り直しは、方式によらず約 50ms**（micro を 1 つでも作り直すと）。60fps の 1 コマ 16.7ms の約 3 倍。ブロックを置く・こわす（`rebuildChunk` に当たる処理）たびに 3 コマ止まる計算。ゲーム本体は今 135.8ms なので悪化ではないが、「常に 60fps」には足りない。
5. 起動 5 秒: 見える範囲を全部作る時間は hybrid r=16 で 0.4 秒、r=24〜32 で 1 秒、全部 micro だと 2.2〜2.6 秒（生成 77ms・光 128ms の前後に足されるので、全部 micro は危ない。hybrid なら入る）。
6. 上空（島全体を見下ろす）の数は、hybrid が「水平の距離」で近い遠いを決めているので、カメラが 100 ブロック上でも真下が micro で描かれ、実際より重く出る。地面で遊ぶときは当てはまらない（スタートの値が実プレイに近い）。

## メモリへの影響

- **メッシュ**: 近くを micro にした分だけ増える。hybrid r=16 で 30〜70MB（CPU と GPU で約 2 倍 → 60〜140MB）、全部 micro は 200〜350MB（×2）。M4（ユニファイドメモリ）なら r=16〜24 は余裕。全部 micro は避けたい。
- **一度作ったメッシュを捨てていない**（hybrid で近さが変わっても隠すだけ）。歩きまわると増え続けるので、本番は近さが変わったら捨てる、または上限を決める。
- **localStorage（今の保存）**: この試作の「見た目だけ 9×9×9」なら**保存・世界のデータは今のまま**（世界 `Uint8Array` 約 786KB、小ブロックの形は位置のハッシュで毎回決まるので保存しなくてよい）。小ブロックを本当に掘れるようにすると、全マスを細かくするのは 128×48×128×729 ≒ 5.7 億マスで不可能。「細工したブロックだけ」小ブロック（1 ブロック 729 バイト）で持つとしても、約 7,000 ブロックで localStorage の 5MB を超える。IndexedDB か差分のランレングスが要る。
- 3D テクスチャ（色の模様）: 27×27×27×4 バイト×ブロックの種類数 ≒ 数百 KB〜1MB。無視できる。

## 改善案（優先度順）

1. **【本番の方式】hybrid（近く＝小ブロックの形、中くらい＝箱＋模様、遠く＝LOD）にする。** 全部を小ブロックの形にする方式（naive/greedy）は、三角形・メモリ・作る時間のどれも合わない。
2. **ブロックの変更で micro を作り直す時間（約 50ms）を 16ms 以下にする。** 案: ①変更した 1 ブロックのまわりだけ作り直す（チャンクを縦や 8×8 に細かく分ける）、②作り直しを Worker に出す、③先に箱＋模様の絵で出して、あとから micro に差しかえる。
3. **でこぼこの量を絵の側で決める（アートの宿題）**: 段差を「面の数が増えにくい形」に（上面だけ・段差は 1 段・3×3 のかたまりなど）すると、三角形がそのまま減る。同じ見た目をシェーダーの模様で出せる所は形にしない。
4. **隠したメッシュを捨てる／上限を決める。** 近さの判定を、水平だけでなく 3D の距離にする。
5. **頂点を詰める**（今 1 頂点 10 バイトで既に小さい）: 四角ごとの index をやめてインスタンス描画にする、などはまだ要らない。r=16〜24 に収まるなら不要。

## 結論・#28「決めること」への材料

| # | 決めること | 材料 |
|---|---|---|
| 1 | 小ブロックを本当に掘れるか | **見た目だけ 9×9×9 なら今の仕組みで足りる**（世界・保存・当たり判定が変わらない）。掘れるにすると、世界のデータ・保存・作り直しが全部作り直し。まず「見た目だけ」で Mac の fps と見た目を確かめてから、掘りたいかを決めるのがよい。 |
| 2 | ふつうと細工したブロックで持ち方を分けるか | 掘れるようにするなら**分ける一択**（全部を 729 倍にすると 5.7 億マス）。見た目だけなら分ける必要がない。 |
| 3 | 物理・光・当たり判定を 1 マス単位のままにするか | メッシュを作る時間の半分以上は形の面の数なので、物理・光まで細かくする理由は性能からは出てこない。**1 マス単位のままが安全**（光は micro の面の明るさを今の上 1.0・横 0.8・下 0.6 の固定にしてあるのでそのまま乗る）。 |
| 4 | 保存を IndexedDB／ランレングスにするか | 見た目だけなら**不要**（今の差分保存のまま）。掘れる場合は必要（上の「メモリ」参照）。 |

**おすすめ: hybrid の r=16 を既定、Mac で余裕があれば r=24。** r=32 は上空で 520 万三角形・130MB になり、見た目の差に対して重い。r=16 と r=24 の違いは「数ブロック先の草のふさが見えるか」だけなので、Mac で見比べて決める。

## オーナーに Mac で見てほしいところ

この試作は F3 の表示ではなく、**画面の右上に自分で fps を出す**（直近 120 コマの平均と最悪の ms）。目標は **60fps、最悪が 20ms 前後以下**。

1. `npm run dev` → ブラウザで次の URL を開く（Chrome か Safari。ウィンドウは遊ぶときの大きさに）。
   - http://localhost:5173/voxel-proto.html?mode=hybrid&r=16
   - 上のボタンで `r=24`、`r=32` も切りかえられる。
2. 方式ごとに次をする。数字は 5 秒くらい待ってから読む。
   - 「スタート」を押す（島の中心を見る）→ fps と最悪 ms を読む。
   - 「ぐるっとまわる」を 20 秒 → fps の最悪 ms が大きく跳ねないか（カクつき。チャンクの切りかえで出る）。
   - 「上空」を押す → いちばん重い景色。ここで 60 を切ってもよいが、スタートで切るなら重大。
   - マウスをドラッグして草の近くに寄る（W/A/S/D、Space で上、Shift で下）→ でこぼこの見た目が好みか、近づいても カクカクしないか。
3. 見る順番: `hybrid r=16` → `r=24` → `r=32` → `greedyShape`（重い方式の参考。60 を割るはず）→ `current`（今の描き方。基準）。
4. 見た目: 草のふさ、石のまだらが「ドット感がある」と感じるか。遠くが箱＋模様に変わる境目（r の距離）が気にならないか。
5. 持ち帰ってほしい数: 方式ごとの fps（平均）と最悪 ms（スタート・上空）。画面が大きい（Retina）と描く点が増えて fps が落ちるので、ウィンドウの大きさも一緒に。
