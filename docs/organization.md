# 開発組織図（v0.2）

> ステータス: **壁打ち中**。オーナー（人間）と相談しながら更新していく。

## グラフエンジニアリングの定義（このプロジェクトでの意味）

- **ループ（ノード）**: 各エージェントチームは「作る → レビューされる → 直す」を合格するまで繰り返す。
- **グラフ（エッジ）**: 合格した成果物を次のチームに渡す。問題が見つかれば前のチームへ差し戻す。
- この「ループのつながり」を、最終的な制作物ができるまで回し続ける。

```
             [オーナー確認①: 仕様OK?]                 [オーナー確認②: 完成OK?]
                       │                                       ▲
 要望 ─▶ ┌────────────▼┐      ┌──────────────┐      ┌─────────┴─────┐
         │ デザインループ │ ───▶ │ 開発ループ     │ ───▶ │ テストループ     │ ──▶ PO 受け入れ
         │ 作る⇄レビュー  │      │ 作る⇄レビュー  │      │ 検証⇄判定        │
         └──────▲───────┘      └──────▲───────┘      └───────┬───────┘
                │ 仕様の矛盾・不足       │      不具合チケット         │
                └──────────────────────┴───────────────────────┘
                              （差し戻しエッジ）
```

PO エージェントがこのグラフ全体を動かす（どのノードを次に動かすか、差し戻すかを決める）。

## 体制

| 役割 | 担当 | やること |
|---|---|---|
| **オーナー** | 人間 | 仕様確認（確認①）と完成確認（確認②）だけ行う。りっくんのプレイ観察 |
| **PO** | AI | グラフ全体の進行、タスク分解、ループの終了判定、オーナーへの報告 |
| **デザインチーム** | AI（作る人＋レビュー係） | 遊びの仕様・UI・見た目・受け入れ基準を書く |
| **開発チーム** | AI（作る人＋レビュー係） | 実装・ユニットテスト、コードレビュー |
| **テストチーム** | AI | 自動テスト＋ブラウザで実際に動かしてスクショ確認、合否判定 |

各ループの中に「作る人」と「レビュー係」を分けて置き、自分で作ったものに自分で OK を出さないようにする。

## 各ループの詳細

| ループ | 入力 | 作る | レビュー観点 | 合格条件 | 出力（次へ） |
|---|---|---|---|---|---|
| デザイン | PO のタスク票 | 仕様書 `docs/design/*.md` | 6歳に分かるか、ひらがな/ルビ、受け入れ基準が測定可能か | レビュー係 OK ＋ **オーナー確認①** | 仕様書 |
| 開発 | 仕様書、不具合チケット | コード＋ユニットテスト | 仕様どおりか、テストが通るか、読みやすいか | lint/型/ユニットテスト全部 OK ＋レビュー係 OK | 実装コミット |
| テスト | 仕様書の受け入れ基準、実装 | E2E テスト・スクショ | 受け入れ基準を 1 つずつ確認 | 全基準 OK | テストレポート `docs/test-reports/` |

### ループの安全装置

- 1 つのループは **最大 3 周** まで。超えたら PO が止めて、原因を整理する（必要ならオーナーに相談）
- 差し戻しは必ず「何が・どの基準で・ダメだったか」を書いたチケットで行う

## Claude Code での実現方法（予定）

- PO = メインセッション（オーケストレーター）
- 各チームの「作る人」「レビュー係」= `.claude/agents/*.md` のサブエージェント
  - 例: デザイン係はコードを編集できない、テスト係はソースを編集できない（ツール権限で制限）
- 受け渡しは全部ファイルと Git コミット（あとから何が起きたか追える）
