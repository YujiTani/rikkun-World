# 開発組織図（v1.0）

> ステータス: **決定（v1.0）**。運用の詳細は `CLAUDE.md`、エージェント定義は `.claude/agents/`。

## グラフエンジニアリングの定義（このプロジェクトでの意味）

- **ループ（ノード）**: 各エージェントチームは「作る → レビューされる → 直す」を合格するまで繰り返す。
- **グラフ（エッジ）**: 合格した成果物を次のチームに渡す。問題が見つかれば前のチームへ差し戻す。
- この「ループのつながり」を、最終的な制作物ができるまで回し続ける。

```
             [オーナー確認①: 仕様OK?]                              [オーナー確認②: 完成OK?]
                       │                                                    ▲
 要望 ─▶ ┌────────────▼┐      ┌──────────────┐      ┌──────────────┐      │
         │ デザインループ │ ───▶ │ 開発ループ     │ ───▶ │ テストループ     │ ──▶ PO 受け入れ
         │ 作る⇄レビュー  │      │ 作る⇄レビュー  │      │ 検証⇄判定        │
         └──────▲───────┘      └──▲────────▲──┘      └───┬──────┬───┘
                │ 仕様の矛盾・不足   │        │ 改善チケット   │      │ 性能目標オーバー
                │                   │        │  ┌───────────┴──┐   │ or マイルストーン末
                │                   │        └─ │ 性能最適化ループ │ ◀─┘
                │                   │ 不具合     │ 計測⇄改善提案   │
                └───────────────────┴───────── └──────────────┘
                              （差し戻しエッジ）
```

PO エージェントがこのグラフ全体を動かす（どのノードを次に動かすか、差し戻すかを決める）。

## 体制

| 役割 | 担当 | やること |
|---|---|---|
| **オーナー** | 人間 | 仕様確認（確認①）と完成確認（確認②）だけ行う。りっくんのプレイ観察 |
| **PO** | AI | グラフ全体の進行、タスク分解、ループの終了判定、オーナーへの報告 |
| **デザインチーム** | AI（デザイナー 1 人＋レビュー係 1 人） | 遊びの仕様・UI・見た目・受け入れ基準を書く。仕様書は 1 人のデザイナーが書き、並行して書かせない |
| **開発チーム** | AI（作る人＋レビュー係） | 実装・ユニットテスト、コードレビュー |
| **テストチーム** | AI | 自動テスト＋ブラウザで実際に動かしてスクショ確認、合否判定。性能の数値も毎回記録 |
| **性能最適化チーム** | AI（計測係＋改善係） | 性能の計測・原因分析・改善。呼ばれたときだけ動く |

各ループの中に「作る人」と「レビュー係」を分けて置き、自分で作ったものに自分で OK を出さないようにする。

> 運用の教訓（M1）: 関係する仕様書を 2 人のデザイナーに並行で書かせたら、仕様どうしが食い違った。オーナーの判断で **デザイナーは 1 人、レビュー係は残す（1 人でマイルストーンの仕様書をまとめて見る）** に変更。

## 各ループの詳細

| ループ | 入力 | 作る | レビュー観点 | 合格条件 | 出力（次へ） |
|---|---|---|---|---|---|
| デザイン | PO のタスク票 | 仕様書 `docs/design/*.md` | 6歳に分かるか、ひらがな/ルビ、受け入れ基準が測定可能か | レビュー係 OK ＋ **オーナー確認①** | 仕様書 |
| 開発 | 仕様書、不具合チケット | コード＋ユニットテスト | 仕様どおりか、テストが通るか、読みやすいか | lint/型/ユニットテスト全部 OK ＋レビュー係 OK | 実装コミット |
| テスト | 仕様書の受け入れ基準、実装 | E2E テスト・スクショ・性能の数値 | 受け入れ基準を 1 つずつ確認、性能目標を超えていないか | 全基準 OK | テストレポート `docs/test-reports/` |
| 性能最適化 | テストレポートの性能の数値 | 計測レポート＋改善（小さな改善は自分で、大きな設計変更は開発チームへチケット） | 改善前後の数値比較、遊びの見た目・動きが変わっていないか | 性能目標クリア、かつ既存テストが全部 OK | 性能レポート `docs/perf-reports/` |

### 性能最適化チームの動き方

- **いつも動くわけではない**。次のときだけ PO が呼ぶ:
  1. テストチームの記録で性能目標（60fps など）を超えたとき
  2. 各マイルストーンの終わり（特に M1 の世界描画、M5 の妖怪がたくさん出る場面）
- 普段の性能チェックはテストチームが数値を記録するだけにして、コストを抑える
- 注意: クラウドの AI 環境には Mac の GPU がないので、AI が測れるのは「描画回数・ポリゴン数・処理時間」などの目安。**本当の fps はオーナーの Mac で性能表示（F3）を見て確認**する

### ループの停止ルール（決定）

周回数では止めない。**「同じ・似た指摘が、直したはずなのに再発している」ときに止める。**

1. レビュー係・テスト係は、指摘を出すたびに「指摘台帳」（`docs/loop-ledger/`）に記録する
   - 内容: どの受け入れ基準／どの場所（ファイル・機能）／原因の見立て
2. 新しい指摘が来たら、PO が台帳と比べて **同じ・似た指摘か** を判定する（完全一致でなくてよい）
   - 似ている例: 「妖怪が壁をすり抜ける」と「妖怪がブロックにめりこむ」→ 同じ当たり判定の問題
3. 似た指摘が **直したはずなのに 2 回再発** したら、そのループを止める
   - 別に、1 機能あたり全ループ合計 **10 周** に達したら、指摘に関係なく止める
4. 止めたら PO が「何が・なぜ直らないか・考えられる案」をまとめ、オーナーに相談する
5. これはループ同士の差し戻し（例: テスト → 開発 → テスト …）にも同じルールを使う

差し戻しは必ず「何が・どの基準で・ダメだったか」を書いたチケットで行う。

## Claude Code での実現方法

- PO = メインセッション（オーケストレーター）
- 各チームの「作る人」「レビュー係」= `.claude/agents/*.md` のサブエージェント
  - 例: デザイン係はコードを編集できない、テスト係はソースを編集できない（ツール権限で制限）
- 受け渡しは全部ファイルと Git コミット（あとから何が起きたか追える）
