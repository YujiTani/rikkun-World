# 開発組織図（v2.0）

> ステータス: **決定（v2.0, 2026-10-16）**。全員のルールは `docs/rules.md`、運用とコマンドは `CLAUDE.md`、係の定義は `.claude/agents/`。

## グラフエンジニアリング（このプロジェクトでの意味）

- **ループ（ノード）**: 各チームは「作る → 見る係がレビュー → 直す」を合格（重大 0 件）まで回す。
- **グラフ（エッジ）**: 合格した物を次のチームに渡す。問題が見つかれば前のチームへ差し戻す。
- 自分で作った物に自分で OK を出さない。見た目と音は、絵にして見る・ファイルに書き出して数で見る。

```
オーナー ── 確認①（仕様・アートと音の案えらび）／ 確認②（完成）／ issue の優先度
   │                                               ▲
   │                                          producer（週次の優先度提案）
  PO（まとめ役: issue ごとにスレッドを立てる・判定・オーナーへの報告）
   │
   ├─ デザインループ   designer ⇄ design-reviewer（遊びの仕様・画面の配置・受け入れ基準）
   ├─ アートループ     art-director → pixel-artist / modeler ⇄ art-reviewer
   ├─ サウンドループ   sound-director → composer / sfx-designer ⇄ audio-reviewer（試聴してオーナーが決める）
   ├─ 開発ループ       developer（並列可）⇄ code-reviewer
   ├─ 検証            UI 検査（自動）→ ui-reviewer（変わった画面だけ）
   │                  tester（新しい受け入れ基準の分だけ）／ 全部の E2E は CI
   └─ 性能ループ       perf-engineer ⇄ perf-analyst（呼ばれたときだけ）
```

差し戻し: テスト・UI 検査で NG → 開発ループへ（実装の問題）／デザインループへ（仕様の矛盾・不足）。性能目標を超えた・マイルストーンの終わり → 性能ループ。

## 体制

| 役割 | 係（モデル） | やること |
|---|---|---|
| **オーナー** | 人間 | 仕様の確認①・完成の確認②、絵と音の案えらび、テーマと方向性を決める、issue の優先度、PR のマージ。りっくんと遊んだ感想を指摘として出す |
| **PO** | メインセッション（Opus） | issue ごとにスレッドを立ててグラフを動かす、似た指摘の判定、ループの停止、オーナーへの報告。ゲームのコードは書かない |
| **プロデューサー** | `producer`（Sonnet） | 全 issue を見て、毎週月曜の朝にオーナーへ優先度を提案する |
| **デザイン** | `designer`（Opus・1 人）⇄ `design-reviewer`（Sonnet・1 人） | 遊びの仕様・画面の配置・受け入れ基準。見た目の細かいきまりはアートに任せる |
| **アート** | `art-director`（Opus）→ `pixel-artist`（Sonnet）／`modeler`（Sonnet・ローカル専用）⇄ `art-reviewer`（Sonnet） | 見た目の方向を 3 案 → オーナーが選ぶ → スタイルガイド `docs/art/DESIGN.md` → テクスチャ・アイコン・3D → 見本シートでレビュー |
| **サウンド** | `sound-director`（Opus）→ `composer`／`sfx-designer`（Sonnet）⇄ `audio-reviewer`（Sonnet） | 音の方向を 3 案 → オーナーが試聴で選ぶ → `docs/audio/SOUND.md` → BGM と効果音 → 書き出して数でレビュー |
| **開発** | `developer`（Sonnet・並列可）⇄ `code-reviewer`（Sonnet） | 実装とユニットテスト、コードレビュー |
| **検証** | UI 検査（自動）、`ui-reviewer`（Sonnet）、`tester`（Sonnet） | 画面の崩れの検査、受け入れ基準の確認 |
| **性能** | `perf-engineer` ⇄ `perf-analyst`（Sonnet） | 計測・原因分析・改善。呼ばれたときだけ |

デザイナーは 1 人（M1 の教訓: 2 人で並行に書くと仕様どうしが食い違った）。レビュー係も 1 人で、そのマイルストーンの仕様書をまとめて見る。

## 各ループ

| ループ | 入力 | 作る | 見る観点 | 合格 | 出力 |
|---|---|---|---|---|---|
| デザイン | issue・タスク票 | 仕様書 `docs/design/*.md` | 6 歳に分かるか、受け入れ基準が確かめられるか、画面の配置（大きさごと・いちばん多いとき） | 重大 0 ＋ **オーナー確認①** | 仕様書 |
| アート | 仕様書・`docs/vision.md` | 3 案の見本シート → スタイルガイド → テクスチャ・アイコン・モデル | スタイルガイドどおりか、6 歳向けか、シルエットで分かるか、数（三角形・描画回数） | 重大 0 ＋ **オーナーが絵を確認** | `docs/art/`・素材 → 開発ループ |
| サウンド | 仕様書・`docs/vision.md` | 3 案の試聴 → `docs/audio/SOUND.md` → BGM・効果音 | 音量・音割れ・長さ・ループのつなぎ目、こわすぎない・急に大きくない | 重大 0 ＋ **オーナーが試聴で確認** | 音のデータ → 開発ループ |
| 開発 | 仕様書・素材・不具合 issue | コード＋ユニットテスト | 仕様どおりか、バグ、性能の落とし穴 | `npm run check:fast` ＋重大 0 | ブランチ・PR |
| 検証 | 実装 | UI 検査の結果、新しい受け入れ基準の E2E、スクショ | 受け入れ基準を 1 つずつ、画面の崩れ | 全基準 OK ＋ CI 緑 | テストレポート `docs/test-reports/` |
| 性能 | テストレポートの数値 | 計測レポート＋改善 | 前後の数、見た目と動きが変わっていないか | 目標クリア ＋ 既存テスト OK | `docs/perf-reports/` |

### アートとサウンドの動き方
- 最初に方向の **3 案** を絵（見本シート）・音（試聴ページ）で出し、**オーナーが選ぶ**。AI のレビューが合格でも、オーナーの OK まで決まりにしない。
- 作った物は必ず絵にして見る／書き出して数で見る。見本ページ（`preview.html`）を、テクスチャ・アイコン・妖怪の見本シートと、音の試聴にも使う。
- `modeler` は Blender MCP があるローカルのセッションだけで動く。Blender は 1 つなので並列にしない。
- 9×9×9 の新しい見た目は、世界のデータ・描画・保存・当たり判定の作り直しになる。先に試しの場面で重さを測り、オーナーの Mac で fps を確かめてから計画を立てる。

### 検証の動き方
- **UI 検査（自動）** `npm run check:ui`（`e2e/ui-gate.spec.ts`）: 画面の一覧を 3 つの大きさで開き、はみ出し・重なり・画面の外・字の切れ・ボタンの字の折り返し・押せる大きさ・色と字の大きさを調べる。今わかっている くずれは `e2e/ui-gate/known.json`（issue ごと）にあり、それ以外が出たら落ちる。表に足すのは issue を作ってから。画面を足したら spec の `SCREENS` に 1 行足す。`ui-reviewer` は変えた画面のスクショ（`ui-gate-report/`）だけ見る。基準のスクショとの自動の比べは まだない。
- **テストの層は仕様で決める**: 受け入れ基準ごとに【ユニット】【E2E】【UI 検査】【オーナー確認】の印。ロジックはユニット、E2E は「つなぎ」と 1 機能 1〜2 本の通し、見た目は UI 検査。
- 全部の E2E は CI（GitHub Actions）。エージェントは関係する spec だけ回す。
- ブラウザを MCP で実際に触って見るのは、マイルストーンの終わり（確認②の前）に 1 回。

### 性能の動き方
- 呼ばれたときだけ（性能目標を超えた・マイルストーンの終わり）。普段はテスト係が数を記録するだけ。
- クラウドには GPU がないので、比べるのは描画回数・三角形・処理時間。本当の fps はオーナーの Mac で F3 表示を見る。

## ループの停止

`docs/rules.md` の F。似た指摘が直したはずなのに 2 回再発、または 1 issue で全ループ合計 10 周で止め、PO が「何が・なぜ直らないか・案」をまとめてオーナーに相談する。

## Claude Code での実現

- PO = メインセッション（プロジェクトではまとめ役の Claude）。issue ごとにスレッドを立て、そのスレッドの Claude がループを回す。
- 各係 = `.claude/agents/*.md` のサブエージェント。ツールの権限で「作る係は担当外を触らない」「見る係はソースを直さない」を分ける。
- 受け渡しは全部ファイル・Git・issue／PR（あとから追える）。
