# 計画のクリティカルレビュー（M0 時点）

> `docs/plan.md` v0.3 と `docs/organization.md` v1.0 を批判的に見直した結果。
> 「重大度」は、放っておいたときにプロトタイプのゴール（りっくんが 15 分楽しく遊べる）を外すリスクの大きさ。

## 重大度: 高

### R1. いちばんの目的「妖怪との戦い」を確かめるのが最後（M5）になっている
- **問題**: 「戦いが楽しめる」が最初の目的なのに、戦闘は M5。M1〜M4 を作り込んでから「戦いがつまらない／難しい」と分かると、手戻りが大きい。
- **提案**: マイルストーンの順番を入れかえ、**戦いを M3 に前倒し**する（仮の妖怪 1 種・素手と木の剣・体力・やられて復活まで）。クラフトや食べ物は戦いの「ごほうび・準備」としてあとから足す。
  - 新しい順番（案）: M1 歩ける世界 → M2 掘る・置く・持ち物 → **M3 戦う（最小）** → M4 作る（武器を強くする）→ M5 食べ物・回復・昼と夜 → M6 仕上げ
- **要決定**: 入れかえてよいか。

### R2. 6 歳にキーボード＋マウスの一人称操作はむずかしい可能性が高い
- **問題**: WASD で歩きながらマウスで向きを変える操作は、大人のゲーマー向けの操作。さらにブラウザでは、マウスを画面に閉じ込める仕組み（ポインターロック）が Esc で外れ、子どもは「急にうごかなくなった」と感じやすい。
- **提案**:
  1. **M1 の終わりに、りっくんに操作だけ試してもらう**（3 分でよい）。むずかしそうなら、コントローラー対応を前倒しする。
  2. ブラウザの Gamepad API は比較的かんたんで、入力の変換層（M0 で作成済み）があるので追加コストは小さい。
  3. ポインターロックが外れたら、大きな「クリックしてね」ボタンを出す。
  4. 攻撃はねらいがずれても当たりやすくする（当たり判定を広めに）。

### R3. 罰がかさなると、6 歳にはつらすぎる可能性
- **問題**: 「やられると 50% 落とす」＋「10 分で消える」＋「おなかが減る」＋「夜は妖怪が出る」が重なると、くやしくて遊ぶのをやめてしまうおそれがある。
- **提案**: 決定どおりに作るが、**数値はすべて 1 か所の設定ファイルで変えられるようにする**（落とす確率・消えるまでの時間・おなかの減る速さ・妖怪の強さ）。プレイテストを見て調整する。

### R4. 絵や 3D モデルを用意する人がいない
- **問題**: AI チームは画像やモデルを上手に描けない。特に妖怪のデザインは見た目が大事。
- **提案**: 見た目は **「コードで作れるもの」** に限定する（ブロックを組んだ妖怪、16x16 ドット絵をコードで描いたテクスチャ）。妖怪の相談のときは、AI がブロック妖怪の試作を作ってスクショで見せる流れにする。デザイナーの定義にも反映済み。

## 重大度: 中

### R5. 性能は AI 側では本当には測れない
- **問題**: クラウドには GPU がない。M0 の計測でも fps は画面の更新に合わせて「60」と出るだけで、意味がない。処理時間も GPU の重さは入らない。
- **対策（実施済み）**: 描画回数・ポリゴン数などの「目安」で比べる仕組みを作った。**本当の fps はオーナー確認②のチェックリストに入れて、Mac で F3 表示を見る**。

### R6. オーナー確認①（仕様確認）が機能ごとだと多すぎる
- **問題**: 機能が 11 個あると、仕様確認が 11 回以上になり、オーナーが待ちのボトルネックになる。
- **提案**: 確認①は **マイルストーン単位でまとめて 1 回**。`CLAUDE.md` に「まとめてよい」と記載済み。
- さらに、**マイルストーンごとに PR（プルリクエスト）を作り、オーナーが OK したらマージ**、を確認②の合図にすると、記録が残って分かりやすい。

### R7. オーナーが Mac で遊ぶ方法が決まっていない
- **問題**: 今は `npm run dev`（Node.js が必要）でしか遊べない。毎回コマンドを打つのは手間。
- **選択肢**:
  1. **GitHub Pages で公開** → URL を開くだけで遊べる（いちばんかんたん。ただしリポジトリが非公開だと有料プランが必要）
  2. Mac に Node.js を入れて `npm run dev`
- **要決定**: どちらにするか。

### R8. 「似た指摘か」を判定する PO が、進行役も兼ねている
- **問題**: 進めたい側（PO）が審判もするので、判定が甘くなりがち（「これは別の指摘」として周回を続けてしまう）。
- **対策**: 判定の理由を台帳に必ず書く。停止したときはオーナーが台帳を見られる。10 周の上限も保険になる。今はこれで十分と判断。

### R9. AI のコストと、PO の記憶の限界
- **問題**: サブエージェントは別のサブエージェントを呼べないので、PO（メインセッション）が全部を中継する。マイルストーンが長いと PO の会話が長くなり、前の内容を忘れやすくなる。
- **対策**: 受け渡しはすべてファイル（タスク票・仕様書・台帳・レポート）にした。PO は会話の記憶ではなく、ファイルを読んで状況を判断する。マイルストーンごとにセッションを分けてもよい。

## 重大度: 低

### R10. セーブデータはブラウザの中にしか残らない
- ブラウザのデータを消すと世界も消える。ブラウザ（Chrome か Safari）を 1 つに決めて遊ぶ。プロトタイプ後に「セーブを書き出す」機能を検討。

### R11. 「楽しいか」は自動テストできない
- プレイテストの見るポイントを決めて記録する（`docs/playtests/`）: どこで止まったか、助けを求めたか、何回やられたか、何に笑ったか、自分から「もっとやりたい」と言ったか。

### R12. プロトタイプの機能が 6 歳には多いかもしれない
- 「おなか」は、子どもにとっては面倒なだけになることがある。M5 のプレイテストで判断し、つまらなければ設定で切れるようにする。

## まとめ: オーナーに決めてほしいこと

1. **R1**: 戦いを M3 に前倒しするか
2. **R7**: 遊び方（GitHub Pages か、Mac で `npm run dev` か）
3. **R2**: M1 の終わりに、りっくんに操作だけ試してもらえるか
