# E2E-175: 本当の時間で待つ E2E を、機械の速さにたよらない形に直す

issue: #175 / ルール: #130（ふつうの E2E は機械の速さにたよらない。速さは性能チェックだけで見る）
ブランチ: `claude/project-thread-4jgl6w`

## なぜ
VOX-B（PR #164）で 1 コマが重くなり、GPU のない CI で、本当の時間で待つ E2E が時間切れになりはじめた。遊び・見た目は変えない。テストの期待（合否の条件）も変えない。

## 直すもの（`grep -rnE "waitForTimeout|timeout: [0-9]|setTimeout|performance.now" e2e` で探す）
1. `waitForTimeout(N)` で「アニメーションが終わるのを待つ」「ゲームが進むのを待つ」所
   - ゲームの時間なら: `__rikkun.pause()` → `step(n)` で決まった数だけ進める。
   - CSS のアニメーション（開く・ふわっと出る）なら: その要素の `getAnimations()` が全部 finished になるのを `waitForFunction(..., { timeout: 0 })` で待つ。または `page.emulateMedia({ reducedMotion: 'reduce' })` でアニメーションが止まるならそれを使う（src 側の対応を確かめてから）。
   - 入力のあと UI が変わるのを待つだけなら、その状態を `waitForFunction` / `expect.poll` で待つ。
2. `waitForFunction` / `expect.poll` の小さい決め打ち `timeout:`（5000・8000・10000 など）。ゲームが本当の時間で進むのを待っている所は、描画を止める（`suspendRender(true)`、`e2e/helpers/char.ts` の `waitCharLoaded` と同じ考え）か、コマ送りに変えて、時間の上限はテスト全体にまかせる（`timeout: 0`）。
3. 経過時間そのものを測って合否を決めている所（`m2.spec.ts` の openedIn、`m72.spec.ts` の stepMs、`voxF-save.spec.ts` の syncMs、`m1.spec.ts` の tick が進むまで 1 秒待つ所）: 速さの合否は外して性能チェック（`e2e-perf/`）へ移すか、記録だけにする。何をどう移したかを PR の説明用にメモする。
4. `test.setTimeout` / `describe.configure({ timeout })` で上限を広げただけの所（とくに `craft2.spec.ts:1143` の 300 秒）: 場所づくりをまとめる、`step` の回数をへらす、描画を止めて進めるなどで本当に軽くできるなら軽くする。軽くできたら上限を戻す。むりな所はそのまま、理由をメモ。

## まもること
- 期待（何を確かめているか）は変えない。test.fail()・skip を足さない。
- 手元では、さわった spec と smoke だけ回す（`npx playwright test e2e/<spec>`、`--workers` は付けない）。全部は CI。
- `npm run check:fast` が通ること。
- コミットは小さく、spec ごとくらいに分ける。メッセージは日本語。
