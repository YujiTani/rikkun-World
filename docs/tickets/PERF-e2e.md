# PERF-e2e: E2E を速くする（M6 のあと・別 PR）

オーナー要望（2026-10-12）:「playwright のテストがかなり時間がかかっている。短くする工夫を」→ 案に OK（M6 のあとで）。

## やること（効きそうな順）
1. ページを使い回す: 同じファイルのテストは beforeAll で 1 回だけ開き、テストの間は `__rikkun` で状態をもどす（reset の窓口を足す）。
2. テストでは小さい世界: `?size=64` などで、地形（M5）以外のテストは小さい世界で動かす。
3. 描画を止める: 一時停止・コマ送りで確かめるテストは描かない（`?norender=1`）。スクショのテストだけ描く。
4. ビルド済みで動かす: `vite preview`（webServer をビルド＋preview に）。
5. 回す範囲を分ける: `test:e2e:fast`（いまのマイルストーン＋smoke）と全部。全部はテスト係とマイルストーンの終わりだけ。
6. workers を 2〜3 に固定（CPU 4）。

## 進め方
- perf-analyst が先にテストごとの時間を計る（前）→ perf-engineer が 1・2・5 から入れる → perf-analyst が後を計って比べる。
- テストの中身（確かめていること）は変えない。消さない・skip しない。

## 結果（perf-engineer, 2026-10-12）

計り方: `npx playwright test --reporter=json`（111 本、CPU 4、クラウドの SwiftShader）。前は workers=2、後は workers=3（固定）。AC18(b)「既知の NG」の 1 本は前も後も同じく失敗（今回の変更とは関係なし）。

| | 前 | 後 |
|---|---|---|
| 全体の時間（wall） | 8 分 42 秒（520 秒） | 約 3 分（178 秒、workers=3）/ 184 秒（workers=2） |
| `test:e2e:fast`（smoke + M6 + 部品見本、11 本） | （なし） | 約 25 秒 |
| m1 / m2 / m3 / m5 の合計（テストの時間の足し算） | 172 / 255 / 459 / 53 秒 | 81 / 88 / 86 / 31 秒（workers=2 のとき） |
| 遅い 1 位 | m3 AC17 149 秒 | preview スクショ 12 秒 |
| 遅い 2〜5 位 | m2 AC5 82 秒、m3 AC7/AC8 79 秒、m3 AC3 61 秒、m2 AC30 39 秒 | m2 AC19-21 11 秒、m2 AC28/29 9 秒、m2 AC30 9 秒、m5 AC20 8 秒 |

効いたもの: 項目 3 の「描かない」を、テストを変えずにゲーム側で入れた。`Game.step()` は毎回描くのをやめ、「描く予定」だけ記録し、次のコマ（一時停止中も）か `renderStats()` のときに 1 回だけ描く。`step(1)` を何千回も呼ぶテスト（m3 AC17 など）が一番効いた。スクショのテストは今まで通り描く。
入れたもの: 項目 5（`npm run test:e2e:fast`）、項目 6（workers=3 固定。2 と 3 の差は小さい）。
入れなかったもの:
- 項目 1（ページ使い回し）: 1 本あたりの起動は約 2 秒で、描画の修正後は合計の 1 割ほど。状態のもどし漏れで結果が変わる危険のほうが大きい。
- 項目 2（?size=64）: 島の生成が 128×128 の中心 (64,64) 前提（`GEN_CONFIG`）で、?size を足すには生成の作り直しが必要。開発チームへのチケット案。
- 項目 4（vite preview）: テストが `/src/ui/theme/parts.html` など dev サーバーのパスを開いているので、そのままでは動かない。効き目も小さそう。
