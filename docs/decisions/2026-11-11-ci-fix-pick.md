# 2026-11-11 CI の赤を直す push では、まえに落ちたテストだけを先に回す（#444）

オーナー（yuzu）: 「CI error を修正するたびに、もういちど push してすべての CI をまわしてます。30 分かかる」「私の操作不要でそれを判断するようにしてほしい」「もっと効率よく CI を早く回す方法がないか」。

## きまったしくみ（`ci.yml`。案は `docs/setup/ci-e2e-first.yml`）

**だれも何も操作しない。直しをふつうに push するだけ。**

1. E2E の各シャードは、落ちたテストの一覧（Playwright の `.last-run.json`）を `e2e-last-run-<n>` として残す。
2. 次の push の CI は、同じブランチのまえの回の一覧を集める。落ちたテストが 1〜60 本あれば、ジョブ「E2E（まえに 落ちた テスト）」がそのテストだけを先に回す（`playwright test --last-failed`。数分）。
3. まだ落ちる → 6 シャードは回さず、すぐ赤。スレッドはまた直して push する。
4. 通った → そのまま同じ回で全部（6 シャード）が回る。緑ならマージへ。
5. まえの回が緑・はじめての push・一覧がとれないときは、今までどおりすぐ全部を回す。

テストは「ファイルとテストの名前」で見分けるので、行がずれても当たる。名前を変えた・消したテストは先には回らず、あとの全部で見る。

## スレッドがすること
- 赤を読んで直し、ふつうに push する（`[skip ci]` や draft はいらない）。
- テストの名前が出ない赤（45 分切れ・`npm ci` やダウンロードの失敗・ランナーが止まった）は直さず、回し直しを 1 回。スレッドは API の再実行が使えないので、PR を draft にしてすぐやめる（`ready_for_review` で CI が回る）。同じ形で 2 回つづいたら原因を調べる。
- 回し直しで通ったテストは「ゆれ」なので issue にする（skip・削除で緑にしない）。

## 調べて分かったこと（2026-11-11）
- スレッドの GitHub の道具では `workflow_dispatch`（ワークフローを手で動かす）が 403 で使えない。draft の切りかえは使える。
- CI の待ちは約 30 分。E2E の 6 シャードが 15〜31 分、**ユニットテストのジョブも 19〜25 分**（10-23 は 3 分だった）。
- ユニットの重さは炭鉱の生成のテスト（`mine*.test.ts`）で、全体の仕事 46 分のうち 33 分。直しは #447。
- 見送った案: 落ちた spec をスレッドがコミットのメッセージに書いて draft で切りかえる（操作が多く、「E2E（全部）」をわざと赤にする必要があった）、別のワークフローを API で動かす（権限がない）、変えたファイルから関係する spec だけえらぶ（見おとしがこわい）、シャードを 6 より増やす（無料の同時 20 ジョブをこえて順番待ちになる。yuzu 10-17 の決定のまま）。

## 注意
- 新しい `ci.yml` が入る前に main から分かれたブランチでは、このしくみは動かない（いつも全部回る）。先に main を取りこむ。
- `.github/workflows/` はスレッドから push できない。ワークフローを変えるときは `docs/setup/` に置いてオーナーに入れてもらう。
