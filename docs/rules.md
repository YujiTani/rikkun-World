# 全体ルール（全員が守ること）

2026-10-16 オーナー確認ずみ。チームごとのルールは `.claude/agents/*.md`、組織とグラフは `docs/organization.md`。

## A. 目的と、大事にすること（オーナーのことば）

0. **りっくんは、パパといっしょにゲームを作る「つくり手」。** 自分の発想や感じたことが形になっていくのを体験してもらうことが、いちばん感じてほしい気持ち。テストプレイヤーはいつもりっくん。
1. **りっくん（来年小学 1 年生）が安全に・楽しく遊べること。** そのうえで、りっくんが感動し、ワクワクするような体験・しくみ・デザインを考える。
2. **オリジナルのゲームにする。** ゆくゆくは宣伝して、りっくんくらいの子どもたちに遊んで楽しんでもらいたい。だから「マイクラのまね」から抜け出す。
3. **人の感性がいる判断は、オーナーの OK をもらう。** 絵・音・見た目の方向・遊びの手ざわりなど。AI のレビューが合格でも、オーナーの OK が出るまでは決まりにしない。
4. **ルールは自分たちで育てる。** 各チームのルールも全体ルールも、いつも見直して良くしていく。ただし AI の力はすごい速さで上がっているので、厳しすぎるルールや、今だけしか関係しない細かいルールは足さない。
5. **ルールを足す・変えるときは issue にして、オーナーの確認をもらう**（ラベル `rule`）。

決めるときの順番: 安全・楽しい → main がいつも遊べる（CI が緑）→ オーナーの時間を取りすぎない（確認は少なく・まとめて）→ 速さとコスト。

### テーマ・こわさ・デザインの方向性
- ゲーム全体のテーマ、こわさの度合い、見た目と音の方向性は、**オーナーが自分の感覚で決める**（AI は案を出して壁打ちの相手をする）。決まったら `docs/vision.md` に書き、デザイン・アート・サウンドの各チームはそれに従う。
- 決まるまでは今の仕様（妖怪・こわすぎない）のまま。友好的な妖怪もいてよい（オーナー案）。
- 決まっていること: グラフィックはオリジナルに一新し、1 ブロックを 9×9×9 の小さなブロックで組む（ドット感は残す）。

## B. 仕事の単位
- 仕事は GitHub issue から始める。issue がない仕事はしない（週次の優先度提案でオーナーが選ぶ）。
- 1 issue = 1 ブランチ = 1 PR。PR の本文に `Closes #番号`。PR のマージはオーナー。
- 大きいもの（マイルストーン）は、親 issue と子 issue に分ける。くわしい仕様は今までどおり `docs/tickets/`・`docs/design/` に書き、issue からリンクする。
- ラベル: `team:design / dev / test / perf / ui-art / sound`、`重大度:高/中/低`、種類（バグ・改善・技術的負債・調査）、`rule`。優先度は週次の提案のあと、オーナーの OK で付ける。

## C. 完成の決まり（Definition of Done）
- CI（型・ユニット・E2E 全部、UI 検査ができたらそれも）が緑。落ちたテストを skip・削除して緑にしない。
- 受け入れ基準ごとに、どの層（ユニット／E2E／UI 検査／オーナー確認）で確かめたかが書いてある。
- **テストは実装より先**（#102）: 仕様が合格したら、実装の前に `tester` が受け入れ基準から E2E を書き、こわれる既存テストを直す（消すなら理由を書く）。新しいテストは 1 回回して落ちる（赤）のを確かめ、`code-reviewer` が基準どおりか見てから実装する。ユニットテストは `developer` が先に書く（赤 → 緑）。
- 期待の数は実装に合わせて変えない。変えたいときは `tester`・デザインへ差し戻し、台帳に書く。
- テストは数の決め打ち（角度・座標・個数）でなく、ゲーム（`window.__rikkun`）に聞いて確かめる。くり返す準備は `e2e/helpers/` の共通の関数を使う。
- 画面を変えたら、変わった画面のスクショが PR にある。音を変えたら試聴ページで鳴らせる。
- 性能に関係する変更は、描画回数・三角形・処理時間の前後が PR にある。
- オーナーが遊んだ感想は、オーナーからの指摘として届く（別にプレイテストの記録は作らない）。届いた指摘は issue にする。

## D. 作る人と見る人を分ける
- 自分で作った物に自分で OK を出さない。
- 渡す前の自己チェック: 仕様の数・寸法・個数は、作った人が計算し直してから渡す（レビューの周回を減らす）。
- 見た目・音は「絵にして見る」「ファイルに書き出して数で見る」。コードだけ読んで OK にしない。数で落とすのは安全（音割れ・急な大音量・強い点滅・性能の上限）だけ。長さ・迫力・こわさはオーナーが見て・聞いて決める（仕様に先に数を書かない）。
- **絵・音・モデルは「見本 → 道具や素材 → AI が整える」**（#121）: はじめにオーナーから見本を 1 つもらう（画像・音・ゲームの名前など）。コードだけでいちから作らず、向いた道具（画像から 3D、効果音の生成、本物の楽器の録音素材など）を使い、AI は大きさをそろえる・つなぐ・ゲームに入れる係をする。素材のライセンス（子どもたちに公開してよいか）を確かめて書く。

## E. 止まらないための決まり（利用上限・待ち）
- 1 つのセッションを長く続けない。スレッドは issue ごとに分け、終わったら閉じる。引きつぎは issue とファイルに書く。
- 同時に動かすサブエージェントは 3 人まで。
- **利用上限が近づいたら、止まる前に「解除されたらすぐ動ける」用意をする**: 作業途中をコミットして push し、issue に「どこまでやったか・次にやる 1 手・そのための依頼文」を書く。新しい大きな作業は始めない。
- E2E などの時間は努力目標（短くする工夫を続ける）。守れない数字はルールにしない。
- 全部の E2E は CI（GitHub Actions）が回す。エージェントは関係する spec だけを回し、CI が落ちたら落ちたテストの名前とログだけ読む。
- オーナーの返事待ちのときも、ほかの issue を進める。

## F. 指摘とループ
- 指摘には【重大】（このまま進むと作り直し・テスト不能・遊べない）か【軽微】（言い回し・書き足し・あとで直せる）を付ける。**重大 0 件で合格**。軽微は次のついでにまとめて直す（そのためだけにループを回さない）。
- 指摘は `docs/loop-ledger/<ID>.md` に 1 行ずつ書く。似た指摘が直したはずなのに 2 回再発（3 回目の出現）、または 1 issue で全ループ合計 10 周したら止めて、何が・なぜ直らないか・案をまとめてオーナーに相談する。ループ間の差し戻しにも同じルールを使う。

## G. 見つけた課題の出し方
- 作業中に見つけた「範囲外の問題」は、直さずに issue にする（PR を広げない）。
- 各チームは週に 1 回、自分の観点で気になる点を見直して issue にする（週次の提案の前）。
- `producer` が毎週月曜の朝に、全 issue からオーナーへ優先度を提案する。

## H. 書いてあることを本当にする
- ルールを足すときは、古いルールを消して短くする。`CLAUDE.md` は 1 画面で読める長さが目安。
- 決まったこと（オーナー決定）は日付つきで `docs/decisions.md` に 1 行。
